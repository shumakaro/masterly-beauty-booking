# Authentication and authorization

Статус: реализация этапа 6; итоговые доказательства CI и ограничения приведены в локальном отчете. Публичного production-деплоя пока нет.

## Приватная конфигурация

JWT_SECRET задается только в окружении/.env: минимум 32 случайных байта. Рабочего значения по умолчанию нет. Генерируйте ключ локально надежным генератором и сохраняйте в приватном .env; не отправляйте его в Git или переписку. Если ключ не настроен, auth возвращает 503 до создания аккаунта. DATABASE_URL должен указывать на базу с примененными Alembic-миграциями.

COOKIE_SECURE=true по умолчанию. Для HTTP localhost разрешен false; конфигурация отвергает false при нелокальных CORS origins. CORS_ORIGINS содержит точные scheme+host+port без пути, wildcard не разрешен. Frontend и API должны работать на одном site; для production рекомендуется Nginx с единым HTTPS-доменом и /api. VITE_API_BASE_URL публичен и не содержит секретов.

Из backend можно выполнить python scripts/configure_local.py: он создает приватный .env из шаблона и добавляет случайный ключ без вывода значения. Существующий ключ сохраняется. Строку подключения PostgreSQL нужно настроить отдельно.

## Контракты

- POST /api/v1/auth/register: JSON email, display_name, password, CLIENT/MASTER. ADMIN запрещен. MASTER получает неопубликованный профиль в той же транзакции. Ответ 201 без хеша.
- POST /api/v1/auth/token: JSON email/password -> access_token, token_type, expires_in, user; refresh-cookie выставляется отдельно.
- POST /api/v1/auth/refresh: ротация refresh-cookie; при повторном предъявлении использованного токена отзывается все его семейство.
- DELETE /api/v1/auth/session: отзыв семейства и удаление cookie, 204, идемпотентно.
- GET/PATCH /api/v1/users/me: только собственные данные. PATCH принимает только display_name.
- GET /api/v1/master/profile: только MASTER, профиль выводится по текущему user.id, не по произвольному ID клиента.
- GET /api/v1/admin/overview: только ADMIN, реальные количества пользователей/мастеров/записей.

Для cookie-операций обязательны Origin из CORS_ORIGINS и X-CSRF-Protection: 1. Пользователь браузера не устанавливает Origin вручную: его добавляет браузер. Не браузерный клиент должен передать оба заголовка явно. Это защита через строгую проверку Origin + custom-header/preflight + SameSite, не секретный CSRF-токен. XSS не устраняется CSRF-проверкой.

Пароль: bcrypt cost 12 через прямой актуальный пакет bcrypt. Минимум 10 символов, максимум 72 байта UTF-8; нулевой байт запрещен, усечения нет. SecretStr и обработчик валидации исключают plaintext пароля из ответов. Неверный пользователь и неверный пароль имеют одно сообщение; для неизвестного пользователя выполняется bcrypt с dummy-хешем.

Access: HS256, 15 минут, claims только sub/role/iat/exp/type, проверяются подпись/срок/тип. Роль и активность перечитываются из БД на запрос, пользователь не может повысить права изменением клиентского состояния/JWT. Refresh: opaque 48 случайных байт, 7 дней с абсолютным deadline семейства; в БД только SHA256-хеш. Cookie host-only, HttpOnly, Secure, SameSite=Lax, path=/api/v1/auth. Ротация/отзыв блокируют владельца и токен в одинаковом порядке, чтобы избежать гонок.

Logout отзывает refresh и удаляет access из памяти клиента. Уже скопированный access может действовать до истечения 15 минут: немедленного denylist для access в этой версии нет. Блокировка пользователя действует при следующем серверном запросе. Refresh не хранится в localStorage/sessionStorage и не возвращается в JSON.

## Администратор

Из backend с приватно настроенным окружением:

```powershell
..\.venv\Scripts\python.exe -m app.cli --email YOUR_EMAIL --name YOUR_NAME
```

Пароль вводится скрыто дважды. Не передается аргументом CLI и не зашит в исходниках. Существующий аккаунт не повышается до ADMIN автоматически. Seed предыдущего этапа остается выключенным и неопубликованным; он не создает демонстрационных рабочих паролей.

## Frontend

/login, /register, /profile; защищенные /dashboard, /master/dashboard, /admin. Кабинеты и онлайн-запись описаны в frontend/BOOKING.md. Формы auth используют RHF/Zod, межполевую проверку паролей и ошибки сервера. Access только в модульной памяти; AuthContext держит публичный профиль. Приватный кэш разделен по user ID и очищается при смене аккаунта. При перезагрузке выполняется refresh. Параллельные 401 используют общий promise и одну попытку обновления; циклических повторов нет. Logout считается выполненным только после успешного ответа API. Theme Context сохраняет только настройку цвета, не токены.

## Защита и пределы

Лимитер auth-запросов: 20/минуту/IP по умолчанию, ограниченная память, Retry-After. Это process-local защита; при нескольких workers/инстансах нужен общий storage или лимит на reverse proxy. Не доверять произвольному X-Forwarded-For. Запросы логируются без body/query/Authorization/cookie, с request_id. Ошибки единообразны, есть Cache-Control no-store для приватных/auth-ответов, nosniff, DENY, no-referrer. HTTPS/HSTS и CSP SPA настраиваются на этапе Nginx.

Нет отправки email, сброса пароля, MFA и OAuth: эти функции не заявлены. Recovery будет отдельным расширением. Секрет и рабочая БД не создаются автоматически. Отдельные Playwright-сценарии выполняются через npx playwright test, а не внутри Vitest.
