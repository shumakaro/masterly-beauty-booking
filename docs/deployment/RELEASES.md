# Совместимые выпуски A/B

Выпуск A сохраняет прежнюю прикладную логику и содержит неизмененную миграцию
005. Его API совместим со схемами 004 и 005. Обычный запуск Render сначала
применяет миграции, поэтому переводит 004 в 005 до старта API. Совместимость
API с 004 проверяется отдельно без запуска мигратора.

Выпуск B добавляет расширенные профили, портфолио и фотографии отзывов и требует
005. Возвращаться с B следует на A, оставляя схему 005. Версия до A не знает
005 и не является безопасной целью Render Rollback. Downgrade удаляет новые
поля и не используется для обычного отката приложения.

/api/v1/health проверяет только процесс. /api/v1/ready проверяет подключение,
единственную допустимую ревизию и необходимые столбцы; возвращает
schema_revision и compatible_revisions. Неизвестная, устаревшая или неполная
схема дает 503. Эти проверки выполняются также после миграции при старте.
Ожидание блокировки ограничено 5 секундами, выполнение SQL мигратора — 120,
процесс мигратора — 180. PGOPTIONS приложения не изменяется.

## Порядок обновления

1. Проверить в Render репозиторий, ветку, фактический Auto-Deploy, текущий
   deploy ID/SHA и доступность rollback-артефакта. Не менять настройки или
   выполнять deployment без отдельного разрешения.
2. Проверить идентичность проекта/ветки/БД Neon, ревизию 004, прямой URL
   мигратора, TLS и достаточные права. Сохранить JWT_SECRET и учетные записи.
3. Создать приватную резервную копию pg_dump -Fc по прямому подключению;
   восстановить в НОВУЮ изолированную БД и сравнить данные. Дамп содержит
   пользовательские данные: не хранить в Git, артефактах CI или публичных PR.
4. На отдельной копии Neon проверить 004→005, сохранность прежних данных,
   текущую схему и A/B. Полный pytest с очисткой выполнять на другой
   одноразовой БД *_test, а не на резервной ветке.
5. После зеленого CI вручную развернуть точный SHA A и подтвердить 005,
   готовность API и прежние сценарии. Проверить, что A доступен для возврата.
6. Вручную развернуть точный SHA B. Проверить readiness=005, каталог, фото,
   вход/refresh, права и сценарии записи. Проверки записи в production
   требуют согласованных тестовых учетных записей и разрешения.
7. При сбое B вернуть A без изменения БД. Если повреждены данные, восстановить
   backup в НОВУЮ БД, проверить ее и отдельно согласовать переключение,
   учитывая посещения, созданные после backup. Рабочую БД не перезаписывать.

Перед первой установкой A старый выпуск еще не знает 005. Поэтому build и
репетиция A обязательны до production; для сбоя этой стадии заранее
согласовывается восстановление/исправление, а не слепой rollback старого кода.

Render Free имеет ограниченное хранение rollback-артефактов и не предоставляет
отдельную pre-deploy command; здесь миграции выполняются штатным стартом
backend. Проверять актуальные квоты и окно восстановления Neon в Console.
Showcase seed предназначен только для изолированных *_demo/*_test и не является
шагом production-развертывания.

Локальная проверка не подтверждает фактическую конфигурацию облака.

Автоматические Render PR Preview останавливаются до миграций при
IS_PULL_REQUEST=true. Они могут наследовать URL рабочей БД; безопасная
preview-конфигурация требует отдельной изолированной базы и отдельного решения.
GitHub Actions использует собственный одноразовый PostgreSQL и не зависит от
Render Preview. Эта защита не меняет настройки production-сервиса.
