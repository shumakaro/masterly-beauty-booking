# Запись и кабинеты

`/book/:masterId?offer=...&date=...` доступен CLIENT. Вход возвращает к
выбранной услуге; переход через регистрацию также сохраняет адрес возврата.
Доступность рассчитывает API, время показано с IANA timezone и UTC offset.
Перед отправкой клиент видит мастера, услугу, дату, длительность, адрес и цену.
`/bookings/:id` показывает серверные данные посещения и сохраненные условия.

Нажатие подтверждения защищено блокировкой повторной отправки. POST использует
UUID Idempotency-Key, который сохраняется и при обновлении access token.
При потере ответа сохраняется незавершенная попытка; после перезагрузки можно
восстановить подтверждение с тем же ключом или проверить кабинет. При 409
расписание перечитывается, требуется новый выбор. Никакого локального статуса
«запись создана» до успешного ответа API нет.

Session storage содержит только UUID операции и публичные ID услуги/мастера,
время и ID текущего аккаунта; токены туда не записываются. Данные изолированы
по аккаунтам. После полученного результата попытка очищается. Если браузер
блокирует storage, повтор работает в памяти до перезагрузки; после нее
проверить результат можно в кабинете. Приватные запросы TanStack Query имеют
user ID в ключе и отменяются/удаляются при смене пользователя.

## Действия по ролям

- CLIENT: посещения с фильтром статуса и пагинацией, детали, отмена до начала,
  избранное, создание отзыва после завершенного посещения, изменение/удаление
  собственных отзывов.
- MASTER: свои посещения, отмена до начала, завершение после окончания,
  профиль/публикация, предложения с ценой/длительностью и отключением,
  интервалы рабочей недели, исключения по датам, портфолио по URL с лицензией.
- ADMIN: посещения и отмена с обязательной причиной, состояние пользователей,
  видимость мастеров, создание/изменение/удаление категорий и услуг. Используемые
  объекты при конфликте можно отключить, сохранив историю. Блокировка ADMIN
  и смена роли через эти формы запрещены сервером.

Меню и фильтры кабинета сохраняются в URL. Изменения данных проверяются
сервером; формы показывают ошибки и сохраняют введенные значения. Удаление и
изменение статуса посещения требуют отдельного подтверждения.

Адреса из исходного плана поддерживаются как защищенные переходы к разделам:
`/bookings`, `/favorites`, `/master/services`, `/master/schedule`,
`/master/bookings`, `/master/profile`, `/admin/users`, `/admin/masters`,
`/admin/bookings`. Они перенаправляют в соответствующий кабинет с параметром
`tab`, сохраняя страницу и статус из query string.

## Проверка

Локальные frontend tests включают сохранение ключа после обновления модуля,
изоляцию аккаунтов, очистку подтвержденной операции, storage без доступа и
неизменность Idempotency-Key при повторе после refresh.

`e2e/booking.spec.mjs` и `e2e/workspace.spec.mjs` работают с настоящим API и
PostgreSQL: потерянный ответ после commit, повтор, конфликт двух клиентов,
отмена/освобождение времени, роль мастера, CRUD отзывов/услуг/графика/особых
дат/портфолио, административный каталог, блокировка и отмена с причиной.
Проверяются ширины 320/375/768/1440; PNG входят в browser artifact.

Для этих E2E требуется одноразовая PostgreSQL `*_test`, миграции и
`python -m scripts.seed_browser` с приватным `BROWSER_TEST_PASSWORD` не короче
32 символов. В CI пароль генерируется и маскируется на один запуск, в Git его
нет. Наполнитель создает явно демонстрационные профили и прошлое посещение
для проверки завершения/отзывов. Он не используется для production.

Загрузка файлов с устройства пока отсутствует: портфолио принимает URL.
Почтовые уведомления, оплата и внешние календари не подключены.
